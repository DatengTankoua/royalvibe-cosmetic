## Correction ciblée — switch depuis une organisation suspendue
Problème : `OrganizationGuard` (global) exige que l'organisation **courante du JWT** soit active pour TOUTE route protégée — si elle devient suspendue (ou la membership), un utilisateur multi-org ne pouvait plus lister ses autres organisations ni y basculer.
Mécanisme ajouté (le plus petit possible) : décorateur `@SkipOrganizationContext()` (clé de métadonnée dédiée `skipOrganizationContext`, distincte de `IS_PUBLIC_KEY`). `OrganizationGuard` continue à laisser passer `@Public()` en premier (inchangé), puis vérifie `@SkipOrganizationContext()` et retourne `true` **sans appeler `resolveActiveContext()`** — aucune autre branche modifiée. La route reste entièrement authentifiée : `JwtAuthGuard` (garde globale, exécutée AVANT `OrganizationGuard`) continue d'exiger et de valider le JWT/utilisateur ; rien n'est rendu `@Public()`. Appliqué **uniquement** à `GET /auth/organizations` et `POST /auth/switch-organization`. `AuthService.switchOrganization` appelait déjà `resolveActiveContext(userId, dto.organizationId)` sur la cible demandée (indépendant de l'org courante) — aucun changement nécessaire là ; `listActiveOrganizations` filtrait déjà uniquement les memberships/organisations actives — aucun changement nécessaire non plus. Toute autre route reste inchangée (aucun autre handler décoré).

## Correction ciblée — mode récupération du shell (branding vs liste indépendants)
Problème : le shell chargeait `GET /organizations/current` et `GET /auth/organizations` via `Promise.all` — un 403 sur le branding (organisation courante suspendue) faisait échouer le `.then` en entier et empêchait d'exploiter une liste d'organisations pourtant valide.
Corrigé (`app/app/layout.tsx`) : `Promise.allSettled`, deux états d'erreur indépendants (`brandingError`/`listError`) — l'un n'écrase jamais l'autre. En 403 branding : `organization` reste `null`, message accessible **« Organisation actuelle indisponible. »** affiché (`role="alert"`) sans aucune redirection (le seul effet de redirection du shell reste conditionné à `!user`, jamais à une erreur de branding/liste). Le sélecteur reste alimenté par la liste active (`alternatives`, qui exclut l'org courante **si connue** — quand le branding a échoué, `organization` est `null` donc rien n'est exclu : toutes les organisations actives renvoyées restent proposées) et le switch reste utilisable normalement. Liste active vide (succès, tableau `[]`) → état explicite dédié (message + bouton de déconnexion) à la place du contenu, **sans sélecteur vide** ; une erreur de LISTE (fetch échoué) reste distinctement signalée (`listError`) sans jamais inventer d'organisation ni déclencher ce même état vide. Ancien token conservé jusqu'au succès du switch (déjà garanti par `AuthContext.switchOrganization`, inchangé). `organization-shell-context.tsx` vérifié : déjà minimal (context `{organization}` en lecture seule), aucun changement nécessaire.
**Scénario exact validé** : JWT d'une organisation suspendue → `GET /organizations/current` → 403 (`brandingError` affiché, org courante `null`) → `GET /auth/organizations` → 200, liste des autres organisations actives affichée dans le sélecteur → sélection d'une organisation B → `POST /auth/switch-organization` → 200, nouveau token écrit → `window.location.assign("/app")` (reload complet) → nouveau montage du shell → `GET /organizations/current` avec le nouveau JWT → branding de B chargé normalement, plus d'erreur.
Aucun autre refactor ; pas de framework de test ajouté (toujours aucune infrastructure de test dans `web/`).

## Cycle du switch d'organisation
1. Header shell charge `GET /auth/organizations` (liste) + `GET /organizations/current` (branding) au montage et à chaque `sessionVersion`.
2. Sélection dans la liste API uniquement (aucun `organizationId` libre).
3. `POST /auth/switch-organization` ; **le nouveau token n'est écrit qu'après réponse 200** (`setToken` après l'`await` réussi) → en échec, ancien token/organisation/socket intacts, message d'erreur affiché, aucune redirection. Fonctionne même si l'organisation COURANTE du JWT est devenue suspendue (`@SkipOrganizationContext`) ; la cible demandée reste validée (`resolveActiveContext`) — org inaccessible/inactive → 403 `ORGANIZATION_ACCESS_DENIED` uniforme.
4. En succès : token remplacé, `sessionVersion++`, puis `window.location.assign("/app")` — rechargement complet garantissant contexte/branding/données métier/socket tous rafraîchis avec le nouveau JWT sans toucher aux hooks des pages métier existantes (hors périmètre 1-9B).
5. Garde anti-double-clic synchrone (`useRef`, l'état React seul est insuffisant dans le même tick) + bouton désactivé pendant le switch.

## Cycle Socket.IO
Audit : `useSocket` ne dépendait que de `userId` → un switch d'organisation (même `userId`, JWT différent) ne reconnectait PAS le socket (bug latent). Corrigé : dépendance `[userId, sessionVersion]` (incrémenté à login ET switch) → déconnexion/reconnexion garantie avec le nouveau token. Cleanup au logout/unmount inchangé (déjà correct). `organizationId` jamais transmis par le client — uniquement via le JWT signé côté serveur.
